# 角色、别名与地点登记规则

## 1. 单章角色观察

在首次逐章分析中同时生成 `character_observations`，不要让登记阶段重新读取原文或再次调用模型。一个观察表示某角色在一个 Scene 中的一种出现状态。

必须观察：

- 原文明确具名的人物，即使本章只被提及。
- 有台词的人物，即使只有“守卫”“管家”等身份称谓。
- 具有连续身份的关系角色，例如女主的父亲、国王的弟弟。
- 实际参与画面的稳定身份角色。
- 群众角色候选；只有有台词或在至少两个不同位置重复出现时才进入正式角色登记表。

不要把国家、组织、物品或地点登记为角色。不要把不同国王、不同父亲或不同守卫在缺少证据时强行合并。

## 2. 身份与别名

- `entity_key` 是当前角色概念的简短机器键，只使用小写英文字母、数字和连字符。
- 当前工作包的 `registry_context` 已存在同一人物时，填写其 `matched_character_id` 并复用登记表中的名称；不得重新创建。
- `aliases` 记录原文实际出现的姓名、代词、头衔和关系称谓，但不要把泛指代词作为跨人物匹配依据。
- 同一角色在不同 Scene 各有一条观察，所有已确认说话人片段必须被某条观察引用。
- `candidate_major` 仅表示主要角色候选，最终剧情定位由全书统计和用户确认决定。

### 同一角色的后续确认

把角色实体与角色名称分开维护。不得因为后文确认了真名而重写早期章节，也不得让下游同时统计两个角色。

- `character_allocations` 永久保存每个 `entity_key` 首次获得的角色 ID，不因归并改变。
- `character_key_index` 把所有已确认属于同一人的概念键指向统一角色 ID。
- `character_name_index` 把姓名、译名、头衔和关系称谓指向统一角色 ID；一个称谓可能对应多人时保留多个候选，不得自动选择。
- `character_id_redirects` 把已经对外出现过的旧角色 ID 指向统一角色 ID，使旧数据继续可读。
- 下游必须通过统一解析接口读取角色，不得直接比较名称或绕过重定向。

后文出现明确身份线索时，即使该名称已经先分配了另一个 ID，也要填写 `matched_character_id`。登记阶段将其列为待确认的同一角色，而不是报错或立即误合并。确认归并后，正式名可以提升为后文真名，早期称谓保留为别名。

身份决定追加写入 `data/registries/character-identity.events.jsonl`。通过 `scripts/manage_character_identities.py` 确认或撤销，不要让用户直接编辑 JSONL。归并只重建索引、登记表和确定性下游统计，不重新调用模型。

## 3. 场景地点

已确认或可可靠推断的具体地点进入正式地点登记；`unknown` 和 `conflict` 只进入待确认候选，不分配正式地点 ID。

后续章节若与登记表中的地点一致，复用 `location_id`。Scene 可以使用更具体的子区域名称；登记表保留上级地点和子区域关系，不因名称缩写而丢失制片定位。

## 4. 稳定重建

执行 `scripts/build_registries.py` 时读取所有当前解析视图及身份事件并确定性重建登记内容。角色和地点 ID 的首次分配映射永久保留：章节修订、人工验收、身份归并或新增早期章节不得改变已分配 ID。

机器记录写入 `data/registries/entities.json`；人工查看版写入 `work/registry/entities.md`。后者只展示中文业务标签；同一角色候选使用独立编号和中英双语线索，不暴露实体键、哈希或内部状态值。

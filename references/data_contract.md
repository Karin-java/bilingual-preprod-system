## 1. 目标与边界

V3 只解决开始制作前必须具备的事实整理工作：

- 无损拆分英文原稿，章节编号统一为 `PNN`。
- 每章只进行一次有边界的语义处理，生成中英标准剧本、Scene、Beat 和小型事实增量。
- 本地程序确定性合并角色、地点、出镜与美术资产候选，不重复调用模型。
- 用户决定资产是否制作以及视觉审美；系统不替用户决定造型、色彩、光线、镜头、建筑风格或构图。
- 默认只交付清洗后的 Markdown；只有用户指定某一个文件时，才单独转换为 DOCX。

英文原稿是唯一事实源。`source/original.txt`、章节切片和章节记录中的英文块必须逐字符相互校验。中文翻译、场景划分和事实提取都不能覆盖原稿。

## 2. V2 问题基线与 V3 验收线

### 2.1 已记录的 V2 基线

| 项目 | 实测值 |
|---|---:|
| 全本拆分记录 | 33 个，P00–P32 |
| P02 英文源文件 | 6,944 字节 |
| P02 旧分析包 | 18,167 字节 |
| 旧分析规则 | 6,593 字节 |
| 旧章节 Schema | 9,716 字节 |
| P02 一次实际输入 | 35,954 字节 |
| P01 英文源文件 | 7,325 字节 |
| P01 旧分析结果 | 79,057 字节 |
| P01 最终剧本 Markdown | 17,108 字节 |

旧测试只验证了人工构造的结构数据，没有完成真实模型端到端回归。失败的全本实验还出现了三个重复长请求，P02 没有形成有效输出。这些事实是 V3 必须守住的性能边界。

### 2.2 V3 强制验收线

- 原文重组一致率：100%。
- 默认每章一次语义处理；只有校验失败才创建定向修复任务。
- 全局角色、地点、出镜、资产合并和 Markdown 生成：模型调用次数为 0。
- 单章输入只包含当前章、精简规则和命中的既有实体；规则与上下文开销目标不超过 8 KB。
- 单章结构结果上限：`英文源文件字节数 × 4 + 12 KB`。
- 每个 `PNN` 都是独立检查点；中断后从第一个缺失或失败章节继续。
- 普通运行不要求用户配置第三方模型 API。当前宿主 Agent 直接完成 `next-task.json` 指向的单章任务。

## 4. 单章机器记录

`data/chapters/pNN.json` 由 `schemas/chapter.schema.json` 约束。核心字段如下：

| 字段 | 用途 |
|---|---|
| `chapter_id` | 稳定章节编号，如 `P03` |
| `source_sha256` | 绑定不可变章节原文 |
| `input_sha256` | 绑定本次轻量任务包 |
| `blocks` | 唯一一份英中对应正文；英文块顺序拼接必须重建原章 |
| `front_matter_block_ids` | 章节标题、POV 等连续前置块 |
| `scenes` | 具体生产场景、时间、内外景、概括、Beat 和块范围 |
| `characters` | 本章角色声明及既有 ID 复用 |
| `character_facts` | 人物事实增量，只引用块编号 |
| `locations` | 地点声明和原文明示的空间事实 |
| `appearances` | 实际出镜、回忆、梦境或仅被提及 |
| `identity_links` | 明确同一、疑似同一的角色或地点关系 |
| `asset_candidates` | 本章明确需要关注的服装、道具或状态变体 |
| `issues` | 无法确认且会影响制片或归档的问题 |

每个英文字符只存在于一个 `text_en` 块中。证据字段只保存 `block_id`，不能复制英文引文。中文翻译与英文放在同一块，便于渲染和定向修改。

## 5. 全剧数据库

### 5.1 角色

角色信息只保留生产前必须的信息：

- 编号、英文名、中文名、别名、旧编号重定向。
- 角色类别、重要程度、剧情定位。
- 年龄、性别、种族、身份、外貌、发型、体型、特殊标记、服装、性格。
- 出场章节、具体 Scene、出场方式和原文情节概括。
- 来源块编号、冲突和待确认状态。

缺失字段保留为待确认，不要求每章填满；全文结束后用户可以一次确认或接受未知。

### 5.2 地点

地点只保留：

- 编号、明确名称、别名、归属地点、内外景。
- 原文明示的空间、环境、陈设和状态变化。
- 出现章节、具体 Scene 和剧情用途。
- 来源块编号、冲突和待确认状态。

地点名必须能区分实际生产空间，例如“王宫·维克多的书房”。

### 5.3 出镜

- 实际行动或现场说话记为 `actual`。
- 回忆画面记为 `memory`，梦境画面记为 `dream`。
- 只被谈论记为 `mentioned`，不计入实际出镜矩阵。
- 全角色章节出镜表以角色为行、`PNN` 为列。
- 主要角色场景统计按“一名角色一个独立小节和表格”输出。

## 6. 身份归并与别名解析

同一实体可能先以“King”出现，后以“Viktor”出现。系统不会回写早期章节，而是：

1. 保存两个来源引用和各自名称。
2. 后文有明确证据时读取 `identity_links.relationship=same`；或由用户追加归并决定。
3. 将全部名称、别名和旧编号索引到用户选定的统一编号。
4. 下游无论查询 King、国王、Viktor、维克多或旧编号，都获得同一实体。
5. 撤销归并决定后，从章节事实和仍有效事件确定性恢复。

该机制同时适用于角色和地点，不依赖特定人物名称。

## 7. 美术资产候选

`全文美术资产候选清单.md` 是唯一资产范围清单，字段为：

| 编号 | 类型 | 候选资产 | 剧情明确变体 | 首次出现 | 主要出现位置 | 用户决定 |
|---|---|---|---|---|---|---|

系统会自动列出实际出镜角色、具体场景，以及章节中明确提取的服装、道具和状态变体。用户决定状态包括：

- 待审核
- 已确认
- 合并
- 拆分
- 不制作
- 资料待补充

在用户确认资产范围并补充设计要求之前，不生成角色三视图、场景图或美术提示词。

## 8. 用户交付模板

### 8.1 单章中英标准剧本

```markdown
# P03｜是的，主人

## P03-S001｜内景·王宫·维克多的书房｜日

**本场概括**：……

### P03-S001-B001｜规则改变

**薇奥莱特 / Violette（对白）**

原文：
> “Yes, master.”

译文：
> “是的，主人。”
```

### 8.2 角色信息库

```markdown
## 薇奥莱特 / Violette

| 参数 | 已确认信息 | 原文位置 |
|---|---|---|
| 身份 | 狼族公主；战败后成为奴隶 | P03 |

| 出场章节 | 出场场景（原文位置） | 出场方式 | 情节概括 |
|---|---|---|---|
| P03 | 王宫·维克多的书房（P03-S001） | actual | …… |
```

### 8.3 场景信息库

```markdown
## 王宫·维克多的书房

| 项目 | 信息 | 原文位置 |
|---|---|---|
| 归属地点 | 王宫 | P03 |
| 陈设 | 原文明示内容 | P03 |
```

### 8.4 用户验收问题

```markdown
---

## ISS-P03-0001

**位置**：P03-S001

**需要确认**：本场发生在一天中的什么时间？

**原文线索**：……

**中文参考**：……

**用户答复**：
```

用户文件不显示内部字段路径、当前值或 JSONL。Agent 根据用户按编号给出的答复记录机器事件并局部重建。

## 9. 扩展接口

后续报告或美术提示词模块只读取以下稳定接口：

- `data/catalogs/catalog.json`
- `data/resolved/pNN.json`；不存在时读取 `data/chapters/pNN.json`
- `deliverables/scripts_bilingual/pNN.md` 只供展示，不作为机器事实输入

扩展必须声明读取的 `schema_version`，写入自己的目录或明确的新交付文件，不得覆盖 `source/`、章节记录或全局目录。扩展失败不能让已完成章节失效。
